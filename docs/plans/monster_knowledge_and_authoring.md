# Monster Knowledge, Tactics & Authoring Plan

Status: **planning only — nothing in this document has been implemented yet.**

Three workstreams, done in order because each depends on the one before:

1. **Tactical identity:** every monster has a **combat role**, at least one **vulnerability** and at least one **signature ability**.
2. **Knowledge ladder:** an INT check reveals layered information at results **8 / 10 / 12 / 15 / 20** (never below monster level + 5). Each monster has 2 descriptive hooks, 1 material component and 1 legend, placed randomly on the higher rungs.
3. **Authoring UI:** create new monsters and variants in the app, and attach a photo of the physical miniature.

Design constraint (see memory: no GM): ASH is solo/co-op. The "host" is a device seat, not a referee. Nothing here depends on a GM approving, hiding or revealing information. Monster tactics must be readable by the players themselves, and knowledge belongs to the party.

## 1. Data architecture (foundation for all three workstreams)

Split monster data into **three layers** that merge at load time, each owned by a different process:

```
data/bestiary/stats/*.json        ← generated by ingest (numbers, attacks, cleaned traits). Safe to regenerate.
data/bestiary/profiles/<id>.json  ← hand-authored: role, vulnerabilities, abilities, knowledge ladder, hooks, components.
data/homebrew/monsters/<id>.json  ← created in the UI: new monsters and variants (full or overlay records).
data/homebrew/minis/<id>.<ext>    ← miniature photos.
```

- **Ingest never touches `profiles/` or `homebrew/`.** Re-running extraction is always safe.
- **`data/homebrew/` is outside the release copy list.** Link it into the release with a junction, the same way `music_player/media` already is. Monsters and photos added in a release build then land in the repo and survive updates.
- **One loader, one validator.** A single `loadBestiary()` reads all three layers and validates each record with a zod schema in `src/shared/bestiary-schema.ts`. A malformed or incomplete record **throws** with the file path and field. No `?? placeholder`.
- **Retire the extra sources.** Move the useful parts of `MONSTERS` (content.ts) and `CUSTOM_MONSTER_TEMPLATES` into `stats/` + `profiles/`. Keep `MONSTER_ALIASES` for key aliases only. Delete `BESTIARY_ENTRIES` / `bestiary-data.ts` from the client bundle.
- **SQLite keeps only campaign state** (knowledge, encounters). It no longer holds a copy of the bestiary rebuilt with `INSERT OR REPLACE` on every boot. The in-memory cache built from JSON is the single source.

### 1.1 Schema (shared types)

```ts
type CombatRole =
  | "artillery"   // keeps range; retreats to stay at near/far; attacks from range when possible
  | "bruiser"     // closes to melee regardless of disadvantage; does not retreat
  | "skirmisher"  // hit-and-run; moves after attacking; targets isolated PCs
  | "controller"  // uses conditions/terrain/area effects before damage
  | "lurker"      // ambushes, hides, strikes the weakest, withdraws when seen
  | "soldier"     // holds a line, protects allies, fights in formation
  | "leader"      // buffs/commands others; flees or surrenders when allies fall
  | "swarm"       // many bodies, one stat block; area damage is effective
  | "solo";       // built to fight a whole party alone; multiple actions/phases

interface MonsterTactics {
  role: CombatRole;
  secondaryRole?: CombatRole;
  behaviour: string;          // one-line table instruction, e.g. "Moves to melee even if flanked. Never checks morale while a living enemy is adjacent."
  preferredRange: "close" | "near" | "far";
}

interface Vulnerability {
  tag: VulnerabilityTag;      // controlled vocabulary, for search, UI chips and future rules hooks
  label: string;              // "Cold iron", "Chopping weapons", "Salt"
  effect: string;             // mechanical: "Takes double damage", "Cannot regenerate", "Must pass DC 12 WIS to cross a salt line"
}
// VulnerabilityTag: "cold_iron" | "silver" | "salt" | "fire" | "cold" | "radiant" | "holy_water" | "slashing" | "bludgeoning" | "piercing" | "sunlight" | "running_water" | "true_name" | "music" | "garlic" | "vanity" | "greed" | "other"

interface SignatureAbility {
  name: string;               // "Flit", "Undying", "Infectious bite"
  trigger?: string;           // "When reduced to 0 HP", "On a bite hit"
  effect: string;             // full rule text
  save?: { stat: "str"|"dex"|"con"|"int"|"wis"|"cha"; dc: number | "damage+10" | "damage"; };
  negatedBy?: VulnerabilityTag[];  // zombie Undying: ["radiant", "salt"]
  sourceTraitIndex?: number;  // set when the ability is an existing Shadowdark trait rather than homebrew
}

interface KnowledgeLadder {
  prominentTrait: string;     // rung 1: name + this
  description: string;        // rung 2: appearance, habitat, general behaviour, combat role
  hooks: [AdventureHook, AdventureHook];   // exactly 2, each hints at an ability
  component: MaterialComponent;            // exactly 1
  legend: Legend;                          // exactly 1
  placement: LorePlacement;   // which rung each of the 4 extras unlocks at (see §4.1)
}

interface AdventureHook {
  title: string;
  hook: string;               // descriptive, 1–3 sentences; hints at one signature ability without stating its rules
  hintsAt: string;            // SignatureAbility.name it foreshadows (authoring/test only, never sent to players)
}

interface MaterialComponent {
  name: string;               // "Zombie grave-salt crust"
  harvestDc: number;
  effect: string;             // what it's used for (potion, ward, ritual, trade value)
  valueGp?: number;
}

interface Legend {
  title: string;
  motivation: string;         // what the creature wants
  leverage: string;           // how to outwit it or bargain with it, based on that motivation
}

// Rungs 3 (DC 12), 4 (DC 15), 5 (DC 20). Legend is only ever 4 or 5.
interface LorePlacement {
  hook1: 3 | 4 | 5;
  hook2: 3 | 4 | 5;
  component: 3 | 4 | 5;
  legend: 4 | 5;
}

interface MonsterProfile {
  id: string;                 // matches stats id
  displayName: string;        // "Zombie" (fixes ALL CAPS)
  family: string;             // "Undead", "Fey", "Beast"… (fixes the 281 missing)
  tactics: MonsterTactics;
  vulnerabilities: Vulnerability[];     // min 1
  abilities: SignatureAbility[];        // min 1
  knowledge: KnowledgeLadder;
  miniatureImage?: string;              // path under data/homebrew/minis
}

interface HomebrewMonster {
  id: string;
  kind: "new" | "variant";
  baseId?: string;                      // required when kind === "variant"
  stats: Partial<MonsterStats>;         // full for "new"; changed fields only for "variant"
  profile: Partial<MonsterProfile>;     // same rule
  createdAt: string;
}
```

Variants are **overlays**: the loader resolves `base stats + base profile + variant overrides`, then validates the merged result. Fixing a base monster's profile therefore flows into its variants automatically. Array fields (abilities, vulnerabilities) take an explicit `mode: "replace" | "append"` so the merge rule is never implied.

### 1.2 Worked examples (target content shape)

**Zombie** — role `bruiser`, behaviour "Always advances to melee, even into disadvantage; ignores morale."
- Vulnerabilities: `slashing` "Chopping weapons: a critical hit severs a limb (−1 attack)"; `salt` "Salt on the wound negates Undying."
- Abilities:
  - **Undying** — trigger: reduced to 0 HP. CON save vs damage taken, or it stays down. `negatedBy: ["radiant", "salt"]`.
  - **Infectious bite** — trigger: bite hit. CON save DC 10 + damage, or the target turns into a zombie on their next rest, or immediately if reduced to 0 HP.

**Fey archer (e.g. a sprite type)** — role `artillery`, preferred range `far`.
- Vulnerability: `cold_iron` "Cold iron weapons deal double damage and suppress Flit for 1 round."
- Ability: **Flit** — "Move to near, fire bow, then move to far, all in one round."

## 2. Workstream A — data cleanup (prerequisite)

Do this before any authoring, because roles and abilities are derived from traits.

1. **Fix trait bleed in `extract-monsters.ts`.** Cut each monster's trait text at the next monster's header. Use the next stat-block match's `linesBefore` name index rather than `nextStart`. Add a test: no trait may contain `/AC \d+.*HP \d+.*LV \d+/` or an ALL-CAPS run of 2+ words.
2. **Title-case names** in ingest, with an exceptions map for legendaries ("Obe-Ixx of Azarumme").
3. **Assign families** from TOC depth where available. Otherwise use a reviewed `family-map.json` (id → family), which also serves as the batching key for authoring.
4. **Remove placeholder generators** `generateLoreTiers` / `generateHarvest` from ingest. Stats files carry no lore at all.
5. **Remove silent monster fallbacks** in app.ts / database.ts. An unknown monster key throws `Unknown monster key "<key>"`. Add a startup check that every zone `wanderingMonsterTable` key resolves.
6. Split output into `data/bestiary/stats/{shadowdark-core,cursed-scrolls}.json`.

**Acceptance:** re-running ingest is deterministic; bleed test passes; all 296 have a family; `npm test` green.

## 3. Workstream B — tactical identity + knowledge content (296 profiles)

This is mostly a content job, not a code job. The code is small; writing ~296 × (role, vulns, abilities, 5-rung ladder, 2 hooks, components) is large.

### 3.1 Code
- `src/shared/bestiary-schema.ts`: zod schemas for §1.1, exporting inferred types.
- Loader merges `stats` + `profiles` and throws on any stats id without a profile, **once the coverage gate is on** (see 3.3).
- `tests/bestiary-profiles.test.ts`: every profile validates; every `sourceTraitIndex` points at a real trait; `negatedBy` tags are ones listed in that monster's vulnerabilities; ladder rungs are non-empty and don't repeat each other verbatim.

### 3.2 Authoring process
- **Batch by family** (~25–35 monsters per batch, e.g. Undead, Fey, Giants, Beasts, Cursed Scroll 1…).
- For each batch, a script builds a **drafting brief** from stats + cleaned traits + the variant table's weakness vocabulary (`data/oracles/monster-generator.json`). Profiles are drafted from the brief, written to `profiles/<id>.json`, and **you review each batch** before it's committed.
- **Per-monster content checklist:** combat role + behaviour line, ≥1 vulnerability, ≥1 signature ability, prominent trait, description, **2 descriptive hooks** (each hinting at an ability), **1 component**, **1 legend** (motivation + how to outwit or bargain). `scripts/bestiary/assign-placement.ts` then rolls the seeded placement for any profile that doesn't have one yet.
- **Signature abilities prefer existing Shadowdark traits** (`sourceTraitIndex`). Homebrew abilities are added only where a monster has no distinctive trait (many low-level humanoids and beasts).
- **Licensing** (carried over from `content_and_systems_expansion.md`): ladder prose, legends and hooks are original or paraphrased, never copied flavor text.
- **Role guidelines** so batches stay consistent: ranged attack as the primary attack → artillery; "charge"/multi-attack with no ranged attack → bruiser; paralysis/charm/area → controller; stealth/ambush/invisibility → lurker; etc. Unusual cases are flagged in the brief for your call.

### 3.3 Coverage gate (no fallbacks during the migration)
Showing half-finished profiles with filler would reintroduce the problem we're removing. Instead:
- Profiles are authored and committed batch by batch, with the tests enforcing the quality of **existing** profiles.
- The new Codex/knowledge UI (Workstream C) is built against the profiles, but the old tiered Codex stays until **all 296 profiles exist**. The switch happens in one commit that also turns on "missing profile = startup error".
- Progress is visible with `npm run bestiary:coverage` (per-family counts).
- **Decision:** all 296 are authored before the switch. There is no per-source rollout.

## 4. Workstream C — knowledge ladder mechanics

### 4.1 Rules
Five rungs. Each rung includes everything below it.

| Rung | Base DC | Always unlocks | Plus (by placement) |
|---|---|---|---|
| 1 | 8 | Name + most prominent trait | — |
| 2 | 10 | Description, habitat, general behaviour, **combat role** | — |
| 3 | 12 | **Vulnerabilities + signature abilities** | any of hook 1 / hook 2 / component placed here |
| 4 | 15 | **Full stat block**; sets `acRevealed` on active combatants of that monster | any extras placed here; legend if placed here |
| 5 | 20 | — | any extras placed here; legend if placed here |

**Minimum DC = monster level + 5.** Each rung's effective DC is `max(baseDc, level + 5)`:

```ts
function rungDcs(level: number): [number, number, number, number, number] {
  const floor = level + 5;
  return [8, 10, 12, 15, 20].map((dc) => Math.max(dc, floor));
}
// LV 1 zombie → 8/10/12/15/20
// LV 6 owlbear → 11/11/12/15/20
// LV 12       → 17/17/17/17/20   (a low roll learns nothing; a 17 learns almost everything)
// LV 16+      → every rung needs level+5 (all-or-nothing)
```

`loreTier(total)` in rules.ts is replaced by `unlockedRung(total, level): 0–5`. Store the **raw best total** rather than a rung, so the DCs can change without migrating data.

**Placement of the four extras** (2 hooks, 1 component, 1 legend) is random per monster, with these rules:
- The legend goes on rung 4 or 5.
- The two hooks and the component each go on rung 3, 4 or 5.
- Every one of rungs 3, 4 and 5 gets at least one extra, so no rung above 2 is empty of lore.

The placement is rolled **once, at authoring time**, with a seed from the monster id, and saved in `profile.knowledge.placement`. It never re-rolls between sessions, and it can be edited by hand in the Workshop.

**Fighting a monster** reveals the **DC for each rung** (so the party knows what they need to roll), but no content. Abilities aren't unlocked by fighting: the party sees them happen at the table, and the Codex doesn't spell them out until the check reaches rung 3.

Hooks are **descriptive**. They hint at an ability ("Farmers in Dunmere salt their doorsteps and bury the dead face-down") without stating its rules. The rules text is only shown on rung 3.

### 4.2 Party-level knowledge (replaces per-encounter `lore_tier`)
```sql
CREATE TABLE campaign_monster_knowledge (
  campaign_id INTEGER NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  monster_id  TEXT NOT NULL,         -- canonical id; variants store their own id
  best_total  INTEGER,               -- highest check total ever achieved; NULL = never checked
  fought      INTEGER NOT NULL DEFAULT 0,  -- 1 once the party has been in combat with it → rung DCs visible
  learned_by  TEXT,                  -- character name (flavour only; knowledge is party-wide)
  updated_at  TEXT NOT NULL,
  PRIMARY KEY (campaign_id, monster_id)
);
```
- `encounter:lore` updates it with `MAX(best_total, ?)`. It also works **outside combat**: a new `bestiary:study` action from the Codex, e.g. researching in a library.
- **Combat start** (initiative) upserts `fought = 1` for every monster in the encounter.
- **Variants:** a variant starts from the party's knowledge of its base monster, capped at rung 2 (you recognise the kind of creature, not its new tricks), until the variant itself is checked.
- **Migration:** copy `MAX(encounter_monsters.lore_tier)` per campaign/monster using 1→9, 2→12, 3→15, 4→18 as `best_total`. Set `fought = 1` for every monster that appears in any encounter. Then drop the column's use.

### 4.3 Server-side redaction
- New `GET /api/campaigns/:id/bestiary` (or a state slice on the socket) returns each monster **already redacted** to the party's rung. The client never receives locked content, so there are no spoilers in the bundle.
- **Every seat, host included, sees the party's knowledge.** The host device is a shared screen, not a GM screen.
- Full data is visible only in the **Monster Workshop** (authoring, §5). Opening it shows a clear "spoilers" warning.

### 4.4 UI
- `CodexModal` monsters tab: fetches the redacted bestiary. Detail view has a **ladder** with one row per rung: unlocked rungs show content; locked rungs show "DC 17 — unknown" if the party has fought it, or "DC ? — unknown" if not.
  - Locked rungs don't say *what* they hold (no "a legend is here"), so the random placement stays a surprise.
  - Unlocked rungs render **structured** content (role chip, vulnerability chips, ability cards, component card, hook cards, legend card), not a text blob.
  - A "Study (INT)" button opens the existing physical/digital dice flow and posts `bestiary:study`.
- **Combat tracker:** for monsters at rung ≥ 10 show the role chip and behaviour line (this is what lets a solo/co-op table run monster tactics without a GM). At rung ≥ 12 show vulnerability and ability chips next to the combatant.
- Miniature photo thumbnail on the Codex entry and combatant card, when one exists. Shown at any rung, since the mini is already on the table.

## 5. Workstream D — Monster Workshop (create monsters, variants, minis)

### 5.1 Server
| Route | Purpose |
|---|---|
| `GET /api/bestiary/workshop/:id` | Full, unredacted merged record plus which layer each field came from |
| `POST /api/bestiary/homebrew` | Create a new monster or variant. Body validated by `HomebrewMonster` zod. The merged result must pass the full profile schema, or the response is a 400 listing each failing field |
| `PUT /api/bestiary/homebrew/:id` | Update a homebrew monster or variant |
| `PUT /api/bestiary/:id/profile` | **Edit a core monster.** Writes `data/bestiary/profiles/<id>.json` (role, vulnerabilities, abilities, knowledge, placement). Stat fixes go in the profile's `statOverrides` rather than the stats file, so re-running ingest never loses them. This is also how core monsters that lack lore or vulnerabilities get filled in from the app |
| `DELETE /api/bestiary/homebrew/:id` | Refused (409) if any active encounter or variant references it |
| `PUT /api/bestiary/:id/miniature` | `express.raw({ type: ["image/png","image/jpeg","image/webp"], limit: "8mb" })`, mounted on this route only. Checks magic bytes, writes `data/homebrew/minis/<id>-<sha8>.<ext>`, removes the previous file, and updates the record's `miniatureImage`. Works for core monsters too (the image path goes in a small `data/homebrew/minis/index.json`) |
| `GET /minis/*` | `express.static("data/homebrew/minis")` |

- **Write access:** any joined seat can create and edit, since this is a no-GM co-op table. Changes emit a `bestiary:changed` socket event so every device reloads.
- **Ids:** slug of the name. On a clash, return a 409 asking for a different name (no silent `_2` suffix).
- **Writes are atomic:** write to a temp file, validate by re-loading, then rename. On validation failure the temp file is deleted and nothing changes.
- Also do this outside the upload route: set the global `express.json` limit to `1mb` for large profile bodies, or keep it at 100kb (a text profile is well under that).

### 5.2 Client — `MonsterWorkshop.tsx`
- Entry points: a Codex "New monster" button, and a "Make variant" button on any monster.
- **Variant flow:** pick the base monster, then either roll on the existing variant table (`generateMonsterVariant` becomes a function that pre-fills the form) or edit by hand. Fields show the inherited value with a "override" toggle, so it's obvious what changed.
- **Form sections** mirror §1.1: Stats · Tactics (role picker with the behaviour hint text per role) · Vulnerabilities (tag select + effect) · Abilities (name/trigger/effect/save/negatedBy) · Knowledge ladder (one tab per DC) · Components · Hooks · Miniature.
- Validation runs client-side with the same zod schema, so errors appear inline before submit. The server re-validates.
- **Miniature:** file picker or drag-drop, plus the device camera on a phone (`<input type="file" accept="image/*" capture="environment">`). Crop to square and downscale to ≤1024px with a canvas before upload, then preview.
- **"Promote rolled variant":** encounters created by the encounter generator's 50% variant roll get a "Save to bestiary" action that opens the Workshop pre-filled.

### 5.3 Release
- `update-windows-release.mjs` / `build-windows-release.mjs`: create junctions in the release for `data/homebrew` **and `data/bestiary/profiles`**, like `music_player/media`. Core-monster edits made in a release build then land in the repo too. Remove `profiles/` from the copy step so updates don't overwrite it.
- **Git:** `data/homebrew/monsters/`, `data/homebrew/minis/` and `data/bestiary/profiles/` are all tracked. The upload downscale (≤1024px) keeps photos small enough for the repo.

## 7. Testing

- **Unit (rules):** `rungDcs` for LV 1, 3, 6, 10, 15, 20; `unlockedRung` boundaries at each DC ±1; variant knowledge cap at rung 2; variant overlay merge (replace vs append).
- **Placement:** seeded roll is stable for the same id; legend is always 4 or 5; rungs 3–5 each get ≥1 extra; hand-edited placement that breaks a rule fails validation.
- **Schema:** every profile and homebrew file validates; exactly 2 hooks, 1 component, 1 legend; each hook's `hintsAt` names a real ability; bad records produce errors naming the file and field.
- **Redaction:** `hintsAt` is never sent to players; locked rungs return only the DC (if fought) or nothing.
- **Ingest:** trait bleed regression; deterministic output; name casing exceptions.
- **Server (supertest):** redacted bestiary only contains unlocked rungs at each rung; host seat gets the same redaction; homebrew create/update/delete incl. 409 on id clash and on referenced delete; miniature upload rejects non-image magic bytes and oversize; atomic write leaves no partial file on validation failure.
- **Socket:** `encounter:lore` and `bestiary:study` raise `best_total` monotonically and set `acRevealed` at 15.
- **Migration:** a seeded DB with `lore_tier` values migrates to the expected `best_total`.
- **Browser (preview):** Codex ladder reveal, Workshop create → appears in Codex and encounter picker, phone-width camera upload.
